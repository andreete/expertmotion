## 1. Scope and roles

| Actor | Does |
|---|---|
| Operator | generates and guards the Ed25519 private key; issues, re-binds, renews and revokes Licence Keys with the `expertmotion-license` CLI on an offline machine; maintains the audit log and `revoked.json`; answers support |
| Local Service (`license` module, bytecode-protected per ADR-007) | computes the Machine Fingerprint, verifies the Licence Key offline, decides `licensed` / `trial` / `updatesExpired`, exposes `GET /license`, `POST /license/activate`, `DELETE /license`, `GET /license/machine-code` (routes owned by API_SPECIFICATION.md), sets the `trial` flag on render `inputProps` |
| Editor (`scr.license`) | shows status, Machine Code, Buy link, key entry; never verifies anything itself |
| Desktop Shell | stores nothing licence-specific except the wrapped Database Key; opens the Buy URL in the system browser |

Everything is offline (ADR-014). No licence server exists at launch. The only network touch points are the Buy link (system browser) and the signed `revoked.json` fetched with the update feed when Private Mode is off.

## 2. Terms used here (owned by GLOSSARY.md unless stated)

| Term | Meaning in this document |

## 3. Licence Key format

### 3.1 Payload (JSON)

| Key | JSON name | Type | Rules |
|---|---|---|---|
| format version | `v` | integer | always `1` for `EM1` |
| licenseId | `lid` | string | ULID (26 chars, Crockford base32); generated by the CLI; stable across re-binds and renewals of the same licence |
| licensee name | `name` | string | as entered at purchase, trimmed, ≤ 64 UTF-8 characters; shown in `scr.license` and on the About screen |
| licensee email hash | `eh` | string | base64url (no padding) of the first 16 bytes of SHA-256(lower-case, trimmed email). The plaintext email is never in the key |
| tier | `tier` | string | `standard` or `pro` (BRD §3.1; `pro` reserved, BRD-026) |
| machineFingerprintHash | `fp` | string | hex SHA-256 of `c1 ‖ c2 ‖ c3` (§5.2); the combined fingerprint, used for audit and display |
| fingerprint components | `fpc` | array of 3 strings | base32 (RFC 4648, no padding) of the three 8-byte component hashes `c1`, `c2`, `c3` (§5.2); needed for the 2-of-3 tolerance rule. A missing component is the base32 of 8 zero bytes |
| issuedAt | `iat` | string | ISO 8601 UTC timestamp, seconds precision |
| updatesUntil | `upd` | string | ISO 8601 date (UTC); default `iat + 12 months` (BRD-001) |
| features | `feat` | array of strings | reserved feature flags; empty at launch; unknown flags are ignored by older builds |
| revocation epoch | `rev` | integer | starts at `0`; incremented by the CLI on every re-bind, renewal or reissue of the same `lid` |

Canonical form: keys sorted lexicographically, no whitespace, UTF-8, minimal JSON escaping, integers in decimal (this equals RFC 8785 JCS for this flat schema). The signature is computed over the canonical bytes and the Local Service verifies the signature over the bytes exactly as received, then parses them; it never re-serialises before verifying.

Example Payload (illustrative values, not a valid key):

```json
{"eh":"3q2-7w8Zp1kLmN0oPqRsTw","feat":[],"fp":"9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08","fpc":["GEZDGNBVGY3TQOJQ","MFRGGZDFMZTWQ2LK","ONSWG4TFOQQGC3TE"],"iat":"2026-11-01T08:00:00Z","lid":"01JB5X7K2QG6V9ZT3M4N8P0R1S","name":"Septi Rahayu","rev":0,"tier":"standard","upd":"2027-11-01","v":1}
```

### 3.2 Signature

- Algorithm: Ed25519 (RFC 8032). Implementation: libsodium (`sodium-native`) or `@noble/ed25519` (pure JS, audited) — TRD.md picks one; both verify the same signatures. The CLI uses the same library.
- Message = `UTF8("EM1") ‖ 0x00 ‖ UTF8(kid) ‖ 0x00 ‖ payloadBytes`. Binding the prefix and the `kid` into the signed message prevents moving a signature between formats or keys.
- Signature length: 64 bytes.

### 3.3 String encoding (what the Creator sees)

```
EM1-<kid>-<BASE32(payloadBytes)>-<BASE32(signature)>
```

| Rule | Detail |
|---|---|
| Alphabet | RFC 4648 base32 (`A–Z`, `2–7`), upper case, no `=` padding; chosen because it has no ambiguous `0/O`, `1/I/l` glyphs and survives email clients, chat apps and OCR better than base64 |
| Separators | exactly three `-` characters between the four fields. Base32 output never contains `-`, so splitting is unambiguous |
| Display grouping | the Operator's email and the `.emlicense` file may insert spaces or line breaks every 8 characters inside a field for readability; the parser removes all whitespace first |
| Normalisation on input | trim; remove all whitespace (including zero-width characters); upper-case; map `0→O`, `1→I`, `8→B` only inside the base32 fields (common OCR/typing slips; the checksum is the signature itself) |
| Length | Payload ≈ 300–340 bytes → 480–545 base32 chars; signature → 103 chars; total ≈ 600 chars (ASM-020) |
| File form | the same string in a UTF-8 text file with extension `.emlicense`; `scr.license.input` accepts drag-and-drop of this file |
| Prefix | `EM1` is the format version. A future `EM2` (e.g. CBOR payload) is parsed by builds that know it; `EM1` stays verifiable forever |

Illustrative (not valid): `EM1-A1-PMRGIZLMMVZCEOSFGMZ2IYLOMNSTGZZ…-Q7ZH4Y2R3VT5XJ6KQ…`

## 4. Signing keys and rotation

| Item | Specification |
|---|---|
| Key pair | Ed25519; one active pair at a time, identified by `kid` (two chars, `A1` first) |
| Public keys in the app | a table `{kid, publicKeyHex, status: active | retiring | revoked, since}` compiled into the bytecode-protected `license` module (ADR-007). Multiple entries so that old keys keep verifying old Licence Keys |
| Private key custody | generated with the CLI on an offline machine (air-gapped laptop or a VM with networking disabled) or stored in a hardware token that supports Ed25519 signing; sealed on disk with a passphrase (libsodium `crypto_secretbox` via the CLI `keygen --seal`); never on the dev server, never in the repository, never in CI, never in a password manager that syncs to the cloud (RISK-021) |
| Backups | two sealed copies on separate USB media in two physical locations, plus one paper copy of the sealed hex; the passphrase stored separately from the media. Restore drill once before launch and once a year |
| Rotation (scheduled) | every 36 months or when the Operator's hardware changes hands: release N adds the new public key as `active` and marks the old one `retiring` (still verifies); the CLI signs with the new key from release N onwards; the old key is set to `revoked` only after `updatesUntil` of the last key signed with it has passed (so every legitimately issued key stays verifiable) |
| Rotation (compromise) | the leaked `kid` is set to `revoked` in an emergency release; every licence signed with it is reissued under the new `kid` from the audit log (§10.4) and delivered by email; `revoked.json` is not involved (the key itself is dead). Creators who do not update keep working on their current build, since the old build still trusts the old key — this is the accepted leakage |
| Unknown `kid` at verification | the Licence Key was signed with a key newer than the installed build: EM-5009 "Update Expertmotion to use this key" rather than "invalid", because the key may be perfectly good |

## 5. Machine Fingerprint

### 5.1 Components (Windows)

| # | Component | Source | Normalisation | Notes |
|---|---|---|---|---|
| c1 | Machine GUID | registry `HKLM\SOFTWARE\Microsoft\Cryptography\MachineGuid` (read via `reg query` or a registry library; standard users may read HKLM) | trim, lower-case | regenerated by a Windows reinstall; cloned with VM images (RISK-027) |
| c2 | Primary disk serial | `systeminformation.diskLayout()` → the device that hosts the Windows system volume (fallback: lowest device index) → `serialNum` | trim, upper-case, collapse internal whitespace, strip non-alphanumerics | changes on disk replacement; some USB-booted or virtual disks return empty → treated as missing |
| c3 | CPU model | `os.cpus()[0].model` | trim, upper-case, collapse whitespace, strip `(R)`, `(TM)`, `®`, `™` | low entropy (many identical laptops) but stable; its job is only to be a third vote |

The Local Service reads the components once per launch (the `systeminformation` call spawns PowerShell on Windows, PERFORMANCE §6) and caches them in memory. Raw values never leave the process, are never logged, and are never written to disk; only hashes are kept.

### 5.2 Hashing

```
SALT_1 = "expertmotion.fp.v1.machineguid"
SALT_2 = "expertmotion.fp.v1.diskserial"
SALT_3 = "expertmotion.fp.v1.cpumodel"
c_i    = first 8 bytes of SHA-256( UTF8(SALT_i) ‖ 0x00 ‖ UTF8(normalised value_i) )     (8 zero bytes if missing)
fp     = hex( SHA-256( c1 ‖ c2 ‖ c3 ) )
```

The salts are public constants (embedded in the app and the CLI). Their purpose is to prevent another application from correlating Expertmotion's hashes with its own hashes of the same identifiers, and to make the hashes format-specific; they are not secrets. Truncation to 8 bytes is sufficient because the hashes are only compared for equality, never used for security.

### 5.3 Machine Code (Creator-facing)

```
MC1-<BASE32( c1 ‖ c2 ‖ c3 ‖ CRC16-CCITT(c1 ‖ c2 ‖ c3) )>      → 26 bytes → 42 base32 chars
```

Example (illustrative): `MC1-GEZDGNBVGY3TQOJQMFRGGZDFMZTWQ2LKONSWG4TFOQQGC3TEAAAQ`. Shown in `scr.license.machinecode` with a copy button; the CLI refuses a Machine Code whose CRC does not match (typo protection, RISK-022). The CLI decodes it into `fpc` and computes `fp`.

### 5.4 Tolerance rule

| Readable components on this machine | Rule |
|---|---|
| 3 | licensed if at least 2 of the 3 component hashes equal the Payload's `fpc` entries at the same position |
| 2 (one missing locally or in the Payload) | both readable components must match |
| ≤ 1 | fingerprint cannot be evaluated → treat as mismatch (EM-5003) and log which components were unreadable so support can diagnose |

Consequences: replacing the disk or a Windows reinstall alone does not invalidate the licence; doing both does (then a re-bind, §8). Two identical laptop models share `c3`; they still differ in `c1` and `c2`, so a key does not transfer between them. A cloned VM image matches all three; this is accepted (ADR-007 boundary, §14).

## 6. Offline verification algorithm

Runs at Local Service start (ARCHITECTURE §5 step 2), on `POST /license/activate`, and as a cheap in-memory re-check before each render preflight (PERFORMANCE §7). All steps are local; no network.

| Step | Action | On failure |
|---|---|---|
| 1 | Normalise the input string (§3.3) and split on `-`; require exactly 4 parts | EM-5006 malformed key |
| 2 | Part 1 must equal `EM1` (or another known prefix) | EM-5006 |
| 3 | Look up part 2 (`kid`) in the embedded public-key table | unknown → EM-5009 ("update Expertmotion"); status `revoked` → EM-5002 |
| 4 | Base32-decode parts 3 and 4; the signature must be exactly 64 bytes; the Payload ≤ 4 KB | EM-5006 |
| 5 | Ed25519-verify the signature over `UTF8("EM1") ‖ 0x00 ‖ UTF8(kid) ‖ 0x00 ‖ payloadBytes` with the public key | EM-5002 invalid signature |
| 6 | Parse the Payload as JSON and validate with the Zod schema of §3.1 (`v === 1`, ULID shape, tier enum, `fpc.length === 3`, dates parse) | EM-5006 |
| 7 | Revocation: load the newest trusted `revoked.json` (§8); if an entry with `lid` exists and `entry.epoch > payload.rev` | EM-5004 revoked |
| 8 | Fingerprint: compute `c1..c3` (§5.2) and apply the tolerance rule (§5.4) against `fpc` | EM-5003 fingerprint mismatch |
| 9 | Updates eligibility: compare the compiled `buildDate` (ISO date of the release, DEPLOYMENT_AND_PACKAGING.md) with `upd`: `buildDate ≤ upd` → covered; otherwise the licence is genuine but does not cover this build | EM-5005 updates expired for this build → state `updatesExpired` (exports behave as Trial Mode; §7) |
| 10 | Clock check (§9): update `lastSeen`, set `clockAnomaly` if the clock went backwards by more than 24 h; never fails the licence | EM-5007 (info) |
| 11 | Persist `{licenseKey, lid, tier, name, upd, status, lastVerifiedAt, clockAnomaly}` in the encrypted database table `license_state` (DATABASE_SCHEMA.md); keep the decision in memory for the session | — |
| 12 | Emit SSE `license.updated {status, tier, upd}` so `hdr.action.license` and `scr.license` refresh | — |

Resulting states: `trial` (no key or a rejected key — the rejected key is kept so the Creator can see the error and copy it to support), `licensed`, `updatesExpired`. The Editor receives only the state and the error code, never the reason internals.

Performance: steps 1–7 are microseconds; step 8 uses the cached components; the full routine runs well under 50 ms after the first component read.

## 7. Trial Mode rules

| Rule | Specification | Status |
|---|---|---|
| Entry | fresh install, no key, or key rejected; also the export behaviour of `updatesExpired` | normative |
| Editor | everything works: import, agents, catalogue, Player, Timeline View, all Output Settings UI | normative (GLOSSARY "Trial Mode") |
| Resolution cap | at render time the Local Service clamps the Output Profile to the **720p row** of PERFORMANCE §3 for the chosen Aspect Ratio (e.g. 9:16 → 720×1280); the Editor shows the chosen resolution struck through with "720p in Trial Mode" | normative |
| Watermark | text **"Expertmotion Trial"**, rendered by the Engine as a top-most layer: anchored bottom-right, text height = **4 % of the output height**, right and bottom margins = 2 % of the output height, white at 85 % opacity with a 1 px dark shadow for contrast, bundled UI font; present on every frame, GIFs and stills included; the Player shows the same watermark in Draft and Full preview so preview = export | normative; the string is a brand mark and is **not translated** (ID variant: "Expertmotion Trial") |
| Who sets the flag | the Local Service injects `trial: true` into the render `inputProps` and the Player props; the Editor cannot change it (the HTTP API has no parameter for it) | normative |
| Notice | export preflight shows EM-5001 (informational) with the two actions "Buy" and "I have a key" (PERFORMANCE §7) | normative |
| Time limit | **none**. Trial Mode never expires functionally | normative (BRD-002) |
| Soft reminder | after 14 days from `firstLaunchAt` (stored in `license_state`), a dismissible `sys.toast` once per 7 days: "You've used Expertmotion Trial for two weeks. Buy a licence to remove the watermark and export in full resolution." | `[Operator decision D-3]` keep / change / remove |
| Agents | fully available (the Creator pays the provider anyway); no artificial limit | normative |
| Project compatibility | a trial project opens unchanged after activation; nothing is stored differently | normative |

Indonesian variants of the strings above are in §16.3.

## 8. Re-bind policy and revocation list

### 8.1 Re-bind (move the licence to another computer)

| Rule | Specification |
|---|---|
| Allowance | 3 self-service re-binds per rolling 12 months per `lid` (BRD-007); counted from the audit log |
| Flow | on the new PC the Creator opens `scr.license`, copies the Machine Code, and sends it with the licence email address (or `lid`) to the Operator (email or the store's support form). The Operator runs `expertmotion-license rebind` (§10.2): same `lid`, new `fpc`/`fp`, `rev + 1`, same `upd`. The new key is delivered by email (§12). The old key's `lid` with the new epoch is appended to `revoked.json` |
| Fourth request within 12 months | CLI refuses without `--override "<reason>"`; the Operator decides case by case (`[Operator decision]`, e.g. small fee, BRD §3.2) |
| Old machine | keeps verifying the old key until it receives a `revoked.json` with the higher epoch (next release, or startup fetch when Private Mode is off). This one-release-cycle leakage is accepted (ASM-021) |
| Self-service without a server | "self-service" means the Creator never needs an account or a call: Machine Code in, key out, within K-07 (≤ 24 h). A web form that runs the CLI automatically is a post-launch option; it would be the first server component and needs an ADR |

### 8.2 `revoked.json`

```json
{
  "v": 1,
  "generatedAt": "2026-12-15T10:00:00Z",
  "entries": [
    {"lid": "01JB5X7K2QG6V9ZT3M4N8P0R1S", "epoch": 1, "reason": "rebind"},
    {"lid": "01JB7A1C9DE2F3G4H5J6K7M8N9", "epoch": 1, "reason": "refund"}
  ]
}
```

| Rule | Specification |
|---|---|
| Semantics | a Licence Key is revoked when an entry with its `lid` has `epoch > payload.rev`. Issuing a replacement key with `rev = epoch` keeps the replacement valid and kills every earlier key for that `lid` |
| Reasons | `rebind`, `renewal`, `refund`, `fraud`, `keyrotation` (informational; the Editor shows only EM-5004 copy) |
| Signing | detached Ed25519 signature file `revoked.json.sig` over the exact bytes of `revoked.json`, same key table and `kid` as Licence Keys, message prefix `EMREV1` instead of `EM1` |
| Shipping | embedded in every release (`resources/license/revoked.json` + `.sig`); additionally fetched from the update feed host at startup when Private Mode is off, at most once per 24 h, verified, and stored under `%APPDATA%\Expertmotion\data\revoked.json` |
| Monotonicity | a fetched or embedded list replaces the stored one only if its signature verifies and `generatedAt` is newer; an attacker cannot roll the list back by supplying an older signed copy |
| Size | one line per entry; thousands of entries remain a few hundred KB; no pruning needed in the first years |
| Trial Mode interaction | revocation puts the install into `trial`, keeps projects intact, shows EM-5004 with the support action |

## 9. Clock-tamper handling

| Rule | Specification |
|---|---|
| Stored value | `lastSeen` = the latest wall-clock time observed by the Local Service, written to `license_state` at startup, every hour while running, and at shutdown; a copy is wrapped with the Database Key material in `keyring.bin` (ARCHITECTURE §8) so deleting the database alone does not reset it |
| Detection | at startup and hourly: if `now < lastSeen − 24 h` → set `clockAnomaly = true`, log the two timestamps (no other data), raise EM-5007 (info, shown once in `hdr.action.license` as a small badge "clock changed") |
| Effect on the licence | **none**. The licence is perpetual; `licensed` stays `licensed`. The flag exists for support diagnosis and to disarm the incentive to tamper |
| Effective time | `effectiveNow = max(lastSeen, now)` is used for: the Trial soft reminder, the update-feed eligibility check (a release whose `releaseDate > upd` is not offered by the updater), and the `revoked.json` freshness comparison |
| Build-date check | §6 step 9 compares `buildDate` with `upd` and does not use the clock at all, so rolling the clock back cannot make an uncovered build covered |
| Forward jumps | ignored (a forward jump only makes `lastSeen` larger, which is harmless: it can at most hide a reminder) |
| Reset | `lastSeen` is never reset by the Creator; it is replaced when a Backup is restored on another machine (the restored value is accepted if newer) |

## 10. Issuance runbook (Operator)

### 10.1 Environment

| Item | Specification |
|---|---|
| Machine | the offline signing machine (§4). The CLI and its dependencies are installed from a verified tarball copied by USB; no network |
| Tool | `expertmotion-license` — a small Node CLI in `tools/license-cli/` of the repository (TypeScript, same `@noble/ed25519`/libsodium and Zod schema as the Local Service so the two can never disagree); built on the dev machine, copied by USB, hash checked |
| Inputs that cross the air gap | Machine Codes and licensee details (from the storefront export, by USB); outputs: `.emlicense` files, the appended audit log, the updated `revoked.json` + `.sig` (by USB back to the online machine for emailing and for the next release) |
| Audit log | `audit/licences.csv` on the offline machine, mirrored to the encrypted backup media; columns in §10.3 |

### 10.2 CLI commands

```
expertmotion-license keygen --kid A1 --seal                 # creates kid A1; prints the public key hex for the app table
expertmotion-license issue  --name "Septi Rahayu" --email septi@example.com --tier standard \
                            --fingerprint MC1-GEZD… --updates-months 12 --order ORD-10231
expertmotion-license rebind --lid 01JB5X… --fingerprint MC1-… [--override "disk and board replaced"]
expertmotion-license renew  --lid 01JB5X… --updates-months 12 --order ORD-10977
expertmotion-license revoke --lid 01JB5X… --reason refund|fraud
expertmotion-license verify --key EM1-… [--fingerprint MC1-…]    # offline check; prints the decoded Payload and the EM- code the app would show
expertmotion-license export-revocations --out dist/revoked.json  # writes revoked.json + revoked.json.sig from the audit log
expertmotion-license audit  --lid 01JB5X…                        # history of one licence
```

| Command | Behaviour |
|---|---|
| `issue` | validates the Machine Code CRC; generates a ULID; computes `eh`, `fp`, `fpc`; `iat = now`; `upd = iat + N months` (date only); `rev = 0`; signs with the active `kid`; writes `out/<lid>.emlicense`; appends an `issue` row; prints the key and the email body (§12) with fields filled in |
| `rebind` | checks the rolling-12-month count (< 3 unless `--override`); copies name/eh/tier/upd from the latest row for `lid`; `rev + 1`; appends a `rebind` row and a revocation entry `{lid, epoch: rev}` |
| `renew` | same `lid` and fingerprint; `upd = max(old upd, today) + N months`; `rev + 1`; revocation entry for the old epoch (optional — an old key with an earlier `upd` is harmless; `[Operator decision]`, default: do revoke, to keep one live key per licence) |
| `revoke` | appends a `revoke` row and a revocation entry `{lid, epoch: currentRev + 1}` so no issued key for this `lid` remains valid |
| `verify` | reproduces §6 steps 1–7 (and 8 when a Machine Code is given); used for support (§13) |
| `export-revocations` | rebuilds the full list from the audit log (idempotent), signs it, prints the entry count; the file goes into the release and to the update feed |

The CLI never prints the private key, never sends mail, and refuses to run if it detects a network interface that is up (`--allow-network` exists only for the `verify` command on the online support machine, which holds public keys only).

### 10.3 Audit log CSV columns

`timestamp_utc, action, lid, kid, rev, name, email, tier, fp_hex, machine_code, updates_until, order_ref, reason, operator_note`

Rules: append-only; one row per action (`issue`, `rebind`, `renew`, `revoke`, `refund`, `reissue`); `email` is the only plaintext personal datum besides `name` (BRD-023 limits collection to name, email, Machine Code); retention per BRD-023 (`[Operator decision D-6]`); deletion requests are honoured by replacing `name` and `email` with `deleted` while keeping `lid`, `rev` and `fp_hex` so revocation and re-bind accounting still work.

### 10.4 Reissue after key rotation or compromise

1. Add the new `kid` (§4) and ship the release that trusts it.
2. `expertmotion-license reissue --all-active --kid B2` re-signs the latest row of every non-revoked `lid` with the new key, `rev + 1`, writes one `.emlicense` per licence and an email batch file.
3. Send the batch (online machine) with the §12 template variant "Your updated licence key".
4. Revocation entries are not needed for a dead key, but are added anyway for `keyrotation` so a stolen old key cannot be revived on a build that still trusts the old `kid`.

## 11. Refund and revoke procedure

| Step | Action | Who |
|---|---|---|
| 1 | Refund request arrives within the window (14 days of first purchase; BRD-008, `[Operator decision D-5]`) with order reference or licence email | Creator → Operator |
| 2 | Operator verifies the order in the storefront and finds `lid` via `audit --email` (hash match) | Operator (online machine, public data only) |
| 3 | Operator asks the Creator to deactivate (`scr.license` → "Remove key", `DELETE /license`), which returns the install to Trial Mode immediately; not mandatory — step 4 covers non-cooperation | Creator |
| 4 | `expertmotion-license revoke --lid … --reason refund`; `export-revocations`; the new `revoked.json` is uploaded to the update feed the same day and included in the next release | Operator (offline machine → USB → online) |
| 5 | Refund issued through the storefront; `refund` row appended with the order reference | Operator |
| 6 | Confirmation email EN/ID (§12.3) | Operator |
| Fraud / chargeback | same as steps 4–5 with `--reason fraud`; no reissue for that `lid`; the email hash is noted in `operator_note` for future orders | Operator |

## 14. Threat notes (details in THREAT_MODEL.md)

| Threat | Assessment | Decision |
|---|---|---|
| Patched binary that skips §6 or forces `licensed` | feasible for a motivated attacker despite bytecode protection and ASAR integrity (ADR-007) | **accepted**; the licence protects revenue from casual sharing, not from crackers; no online enforcement at launch |
| Key sharing between two computers | blocked by the fingerprint unless the machines are clones; VM clones pass | accepted (RISK-027) |
| Forged key | requires the private key; Ed25519 with a 32-byte public key embedded; forgery infeasible without compromise | mitigated by key custody (§4, RISK-021) |
| Replay of an old `revoked.json` to un-revoke | blocked by signature + `generatedAt` monotonicity (§8.2) | mitigated |
| Clock rollback | no gain (§9) | mitigated |
| Extraction of personal data from a key | only `name` (chosen by the buyer) and an email hash; the Machine Code reveals nothing about the hardware without the raw values | mitigated |
| Privacy of hardware identifiers | raw `MachineGuid`, disk serial and CPU model never leave the machine; salted truncated hashes only | mitigated |
| Malicious `.emlicense` file | parsed as a bounded string (≤ 4 KB payload), base32 only, Zod schema; no code paths depend on its content before signature verification | mitigated |
| Local Service `POST /license/activate` abuse by another local process | requires the Service Token (ADR-005); worst case: the attacker activates or removes a key on the victim's machine, which they could also do via the UI | mitigated |
| Loss of the private key (not theft) | all future issuance stops; existing keys keep working forever | mitigated by backups (§4) |

What this document does not promise: it never says the licence "cannot be bypassed"; marketing and UI copy must follow the same rule (GLOSSARY "Words to avoid").

## Implementation notes (Stage 3, 2026-10-24; provisional until the Operator confirms)

These choices were made while implementing `apps/service/src/license/` and `tools/license-cli/`, where this document left a detail open.

| Topic | Choice |
|---|---|
| Status names | `trial`, `active`, `invalid`, `revoked`, `updates-expired` (the `license.status` CHECK was extended). A rejected key is `invalid` and keeps Trial Mode exports. |
| Machine Code checksum | CRC-16/CCITT-FALSE (polynomial 0x1021, init 0xFFFF). |
| `revoked.json.sig` | One line `EMREV1-<kid>-<BASE32(sig)>`, signed over `"EMREV1" ‖ 0 ‖ kid ‖ 0 ‖ bytes`. `generatedAt` is the time of the latest revoking audit row, so repeated exports are byte-identical. |
| Fingerprint sources | Windows disk serial from `Win32_DiskDrive.SerialNumber` of the system volume (lowest disk index as fallback) via `execFile`; CPU from `os.cpus()[0].model`. |
| Sealed signing key | scrypt + AES-256-GCM (libsodium is not a dependency); passphrase from `EXPERTMOTION_LICENSE_PASSPHRASE` or `--passphrase-file`. |
| Signature strictness | Strict RFC 8032 (`zip215: false`); the payload `fp` must equal SHA-256 of `fpc`. |
| Clock check | Runs on every path, Trial Mode included, so `lastSeen` keeps moving forward. |
| CLI policy | `issue` needs a Machine Code; rebind revokes the previous key; the fourth rebind within 12 months is refused with EM-5008 unless `--override "<reason>"` is given and logged; renew revokes the previous key; signing refuses to run while a network interface is up (`--dev-allow-network` for development only). |
| CLI exit codes | 0 ok, 1 key not valid, 2 usage, 3 refused by policy, 4 environment. |
| Production key | `PRODUCTION_PUBLIC_KEY_A1_HEX` in `keys.ts` is a placeholder; until the Operator runs `keygen --kid A1 --seal` and pastes the public key, every key reports EM-5009. |
