## 1. How to read this register

| Column | Values |
|---|---|
| Category | `legal`, `technical`, `product`, `security`, `schedule` |
| Owner role | the role accountable for the mitigation (today every role is held by the Operator; the role name stays so the register survives a hand-over) |
| Likelihood / Impact | `L`, `M`, `H` (qualitative; re-assessed at each review) |
| Trigger / early warning | the observable event that means the risk is materialising |
| Status | `open`, `mitigating` (a mitigation is in progress), `accepted` (consciously carried; residual risk documented), `closed` (no longer possible), `occurred` (it happened; see process.md) |

Exposure for ordering = likelihood × impact with L = 1, M = 2, H = 3. Risks with exposure ≥ 6 are reviewed at every gate; the rest at every second gate.

## 4. How to update this register

1. Anyone (Operator, coding agent, reviewer) who discovers a new risk adds a row with the next free `RISK-` number, fills every column (owner, likelihood, impact, mitigation, trigger are mandatory; INDEX.md matrix "Risk → owner" checks this) and records the addition in `process.md`.
2. Never renumber or delete rows. A risk that can no longer happen is set to `closed` with a one-line reason; one that happened is set to `occurred` with a pointer to the `process.md` entry describing what was done.
3. When an assumption is refuted, set its status to `refuted`, add the resulting `RISK-` or `ADR-` reference in the "If false" column, and update the dependent documents listed in the header.
4. A change of likelihood or impact must cite the evidence (measurement, ticket count, external announcement) in the mitigation or trigger column; do not change ratings from memory.
5. Documents that reference a risk (BRD.md §11, ADRs, POC_PLAN.md) link by ID only; the description lives here.
6. Every new user-facing string introduced by a mitigation gets its Indonesian variant in the owning document (ADR-012).
